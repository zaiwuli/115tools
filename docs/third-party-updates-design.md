# 第三方组件更新机制设计

状态：待确认；本次仅设计，不修改依赖、不启用定时检查。

## 1. 设计结论

增加“组件更新”能力，让系统定期发现 p115client 和解压组件的上游变化，并显示当前版本、可用版本、兼容状态和更新记录。

推荐默认行为：每天自动检查，发现变化后提示；只安装本项目验证过的版本。初期通过更新整个应用镜像交付组件升级，不在正在运行的容器内执行 pip install，也不直接覆盖解压程序。

用户不需要维护第三方库源码，但本项目仍需维护与它们的适配、测试以及已有安全修改。上游发布新代码不等于它已兼容本项目。

“允许更新”不等于取消版本固定：构建仍固定到明确的提交、锁文件和镜像摘要；通过更新这些固定值发布新版本，保证可复现和可回滚。

## 2. 当前实现及限制

| 组件 | 当前方式 | 实际更新需要 |
| --- | --- | --- |
| p115client | pyproject.toml 固定 Git 提交 `856e4f8f09ce034534bd458f06d3dee4474a1698`，uv.lock 锁定依赖，Docker 使用 frozen 安装 | 更新提交及锁文件、验证适配接口、重新构建应用 |
| xtractr 解码源码 | third_party/xtractr 来自 UnpackFlow 提交 `349f58940e031be42f1fc1253579d05c9bb733f2`，本项目有安全修改 | 同步兼容源码、重新应用和验证安全修改、编译 helper |
| 解压 helper | extractor 编译为 bin/115work-extract；Docker 多阶段构建，运行时没有 Go 编译器 | 为目标平台构建新二进制并随镜像发布 |

extractor/go.mod 虽声明 golift.io/xtractr v0.3.2，但 replace 指向本地源码。仅修改 Go 模块版本或执行 go get 不会自动升级实际使用的解码实现。

当前已有 helper 路径覆盖能力，但没有组件版本清单、更新校验、切换和回滚协议，不能直接把它作为自动更新方案。

## 3. 上游来源与版本身份

### p115client

- 可信来源：ChenyangGao/p115client 仓库。
- 检查发行版、标签和配置分支的最新提交；没有正式发布时，显示“上游提交更新”，不能伪装成稳定版本。
- 精确版本使用完整 commit SHA；包版本号只作补充展示。
- 升级同时检查 Python 版本要求、传递依赖变化和许可证变化。

### xtractr

需要区分三个来源，不能合并为一个模糊版本号：

1. golift/xtractr：原始项目，作为上游动态参考。
2. UnpackFlow 的 third_party/xtractr：当前实现的直接来源，优先检查它的相关目录和 path_mapper.go 是否变化。
3. 115work helper：本项目封装协议、安全修改和编译产物。

升级以当前直接来源为主，不自动在 golift 和 UnpackFlow 之间切换。若要改用原始项目，应作为单独的迁移评审。

UnpackFlow 的完整仓库地址、跟踪分支在实现前从现有引用核实并写入来源清单，不能只凭目录名推断。同一仓库其他无关目录的提交不应触发“解压组件有更新”。

建议新增 components.lock.json，记录：组件 ID、仓库、跟踪引用、精确提交、相关源码树摘要、本地补丁集版本、helper 协议版本、构建版本和许可证路径。以此作为版本事实来源，避免代码、文档、UI 分别维护版本。

## 4. 更新状态模型

界面明确区分：

| 状态 | 含义 | 可执行动作 |
| --- | --- | --- |
| 已是最新兼容版 | 当前运行版本与最新已验证版本一致 | 检查更新 |
| 上游有变化 | 上游发现新提交，尚未验证 | 查看变更；不提供直接安装 |
| 验证中 / 验证失败 | 候选版本进入本项目兼容流程 | 查看结果；继续使用当前版 |
| 可用兼容更新 | 已完成测试并有对应应用镜像 | 查看发布说明和更新指引 |
| 检查失败 | 网络、权限、限流等导致本次无法确认 | 保留上次结果并重试 |

“最新上游版本”和“最新兼容版本”分别展示。网络失败不能显示为“已是最新”。生产环境实际启用的版本由运行产物自报，不能从仓库当前代码推算。

## 5. 定期检查

### 应用内检查

- 默认每天一次，可关闭，可选择每周，也可手动检查。
- 以持久化调度任务运行，使用互斥和去重，避免并发检查；加入少量随机延迟。
- 启动不阻塞服务；重启后仅补一次到期检查，不补跑所有错过的周期。
- 使用 ETag / Last-Modified；支持连接超时、有限重试及 GitHub 限流退避。
- 记录上次尝试、上次成功、下次检查、每个组件的检查结果。
- 检查仅请求版本和变更元数据，不下载执行源码，不访问 115 文件，不发送 Cookie 或用户任务信息。
- 仅访问预设可信来源；普通用户不能在界面任意填写可执行更新源。

### 仓库内兼容流程

应用不能自行证明上游兼容，验证由本项目 CI 完成。仓库每日检查候选版本，有变化时创建依赖更新分支 / PR，更新精确版本并执行测试。候选验证失败保留报告，不推到生产。

可以同时监测应用内和 CI：前者服务用户展示，后者服务维护和验证。它们共享组件来源定义，但不互相替代。

本项目另发布一份兼容版本清单，包含应用版本、组件精确版本、支持平台、测试结果链接和不可变镜像引用。应用验证清单来源和签名后用于展示“可用兼容更新”；可信公钥随应用发布，不接受清单自带的新公钥作为信任依据。

## 6. 推荐交付方式：不可变镜像更新

第一阶段采用整体镜像升级，这与当前 Docker 部署方式一致：

```text
定期发现上游变化
  → 更新组件版本、锁文件或 vendored 源码
  → 保留补丁并验证兼容
  → 构建 amd64 / arm64 镜像
  → 发布不可变版本和兼容清单
  → 用户在部署平台更新镜像
  → 新实例自检并展示实际组件版本
```

UI 的按钮叫“查看更新指引”，不能把仅下载清单的动作叫“更新完成”。普通容器没有权限更新自己的镜像；初期不挂载 Docker socket，也不为此增加宿主机管理权限。

本地 Python 部署提供等价的版本化安装步骤：新虚拟环境 + frozen 依赖安装 + 对应 helper，验证后停止旧进程再切换启动目标，保留上一版本目录。

整体镜像意味着更新 p115client 也会重启应用，这是初期有意接受的限制。用户仍可以分别看到两个组件的变化及版本。

## 7. 若后续需要“页面一键独立更新”

作为第二阶段，可使用独立更新执行器或部署平台集成，不混入普通业务进程。

- p115client：优先采用版本化独立 worker，通过稳定 RPC 协议调用。当前 Python 进程已经导入库，直接覆盖 site-packages 无法可靠切换或回滚。
- xtractr：本来就是子进程，可使用版本化 helper 目录、明确的协议握手、SHA-256 与发布者签名验证、架构校验和原子切换。
- 活动任务固定使用开始时选定的组件版本；旧产物在任务结束前保留。先停止派发，排空任务，再切换。
- p115 worker 涉及 Cookie 隔离、调用超时、错误映射和重启恢复，应单独设计，不以简单插件加载代替。

这一阶段成本显著高于镜像方案，建议先交付检查和兼容发布能力，再决定是否值得引入。

## 8. 安装、切换及回滚

更新前停止接收新执行，等待正在执行的下载、解压和文件发布结束。超过等待时间则延后更新，不能为了更新强制杀掉正在写文件的任务。

更新后自检：进程健康、组件身份、适配接口签名、helper 协议和小样本解压。115 连通性检查采用只读请求；远端不可用与本地安装损坏分别呈现，不因 115 临时故障反复切换镜像。

保留上一镜像摘要、组件清单及更新记录。启动失败或本地自检失败时恢复上一镜像；不要自动重复升级同一个失败候选。

依赖更新原则上不附带数据库迁移。若必须迁移数据库，发布前明确向后兼容范围并备份；只有旧应用可读的 schema 才能直接回滚，不能声称换回镜像就一定能恢复。恢复数据库备份需单独确认，防止覆盖更新后新增任务。

## 9. 必须保留的兼容测试

### p115client

- 登录 / Cookie 初始化、只读目录列表、目录 CID 校验、分页及错误码映射。
- 离线提交和状态轮询、磁力链接和种子转换后的下载链路。
- 直链下载、云解压查询、密码错误、超时及本地兜底。
- 超时、取消、限流和返回结构变化；异常中不泄漏 Cookie 或签名 URL。
- PR 默认使用模拟数据和契约测试。真实账号只读冒烟由授权的独立环境执行，不在公开 CI 暴露凭据；提交、删除等真实写操作不作为无人值守检查。

### xtractr / helper

- ZIP、RAR、7z、TAR、ISO、分卷、CUE 和嵌套压缩样本。
- 密码、中文名、超长路径、同名根目录及输入输出协议兼容。
- 路径穿越、符号链接、特殊文件、重复输出、字节与文件数量上限。
- 取消、异常退出、部分输出处理和资源限制。
- 本地安全修改必须有独立回归测试；同步冲突阻断发布，不能自动放弃补丁。
- 为 linux/amd64、linux/arm64 构建并验证；Windows helper 若作为支持产物发布，也需对应测试。

CI 通过只能标记本项目覆盖范围内的兼容，不能宣称所有 115 线上行为和所有压缩格式均已验证。

## 10. 设置页设计

入口：设置 → 组件更新。沿用现有 UI，首屏只展示：

```text
组件更新                          [检查更新]
自动检查 [开启]    检查频率 [每天]
上次成功检查：……                  下次检查：……

p115client
当前：提交 abcdef…    最新兼容：提交 ghijkl…
状态：可用兼容更新
[查看变更] [查看更新指引]

解压组件
当前：helper 版本 / UnpackFlow 提交 / 补丁集版本
状态：上游有变化，尚未通过兼容验证
[查看变更]

更新记录（折叠）
```

每个版本可以展开完整 SHA、来源地址、协议和产物摘要。不要把 go.mod 的 v0.3.2 单独展示成实际解压组件版本。

没有更新权限的只读角色可以查看状态，不能修改检查周期或操作更新。

## 11. 通知

新增可选“组件更新”通知，放在通知设置的更多选项，不混入下载和解压结果。

- 默认仅对新的“可用兼容更新”和检查连续失败需要处理时通知。
- 上游未经验证的每次提交不默认通知，避免刷屏。
- 同一组件和同一候选只通知一次；状态变为兼容可用时允许一次新通知。
- 连续检查失败达到阈值（建议 3 次）后通知一次，恢复成功后可通知一次；按单个组件记状态。
- 遵循通知总开关和专属开关；通知发送失败不影响更新检查。

## 12. 建议接口与数据

建议接口：

- GET /api/v1/components：实际运行版本、上游候选、兼容候选及检查时间。
- POST /api/v1/components/check：管理员触发异步检查，返回操作 ID。
- GET /api/v1/components/history：分页查看检查、验证及部署记录。
- PATCH /api/v1/components/settings：管理员设置自动检查、周期。

初期不提供安装接口，避免后端不能更新容器却暴露虚假的更新操作。

数据库分别保存检查调度、组件观察状态和更新记录；构建版本身份来自随产物附带的只读清单。一个检查操作中两个组件分别成功或失败，不因一个来源不可访问覆盖另一个结果。

## 13. 实施顺序与验收

1. 梳理并固定来源清单、补丁差异及组件版本自报。
2. 建立定时上游检查、候选更新 PR 和兼容 CI。
3. 发布兼容清单及不可变镜像，补齐回滚说明。
4. 实现应用内检查、设置页和去重通知。
5. 按需求再评估独立 worker / 一键更新。

验收要求：重启后周期仍准确；断网和限流不会误报最新；上游变化与兼容更新区分明确；xtractr 同步保留安全补丁；不能安装错误架构或校验失败产物；更新期间任务不受强制中断；旧安装可回滚；p115 和 helper 实际版本可追溯到构建记录。

本方案推荐先实现第 1—4 步，自动检查、验证后发布、用户通过部署平台启用；不默认无人值守安装未经验证的上游最新版。
