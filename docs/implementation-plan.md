# 115tools 开发与改造方案（待审阅）

日期：2026-11-04

本文取代此前 implementation-plan.md 中未确认的技术路线。交接文档保留为历史依据。当前只编写开发方案，不代表功能已实现或兼容性已验证。

## 最新范围调整

用户已确认不需要 CUE/FLAC 音轨切分。该功能不再属于保留范围，旧 helper 与 xtractr 已移除；下文涉及 CUE 保留和兼容 helper 的原计划由本条及 first-version.md 覆盖。普通包内音频文件继续解压。

## 1. 已确定的方向

- Python 作为主程序，复用 115work 现有业务和前端。
- p115client 作为上游 Python 依赖，经适配层调用，不复制上游源码。
- 本地解压采用官方 7-Zip 命令行，不继续以 xtractr 或 xt 为目标解压引擎。
- 所有开发只在 `G:\codex项目\115tools` 进行，旧目录不修改。
- 保留现有功能和任务链行为。存在差异时先补齐、验证；不能静默删除能力。
- 三个模块一起部署为一个应用；不引入三个常驻服务。

## 2. 模块职责

| 模块 | 职责 | 更新方式 |
|---|---|---|
| Python 主程序 | 页面、API、配置、数据库、队列、业务规则、任务链、下载、通知与文件处理 | 项目自身发布 |
| p115client | 115 登录、目录、离线任务、直链和云解压等接口 | 锁定上游精确版本，契约验证后随应用发布 |
| 官方 7-Zip | 压缩格式读取、解密和解压 | 锁定官方版本，样本验证后更新组件或应用镜像 |

分卷归组、密码选择、嵌套调度、提层、CUE 输入识别、输出发布和原包清理由主程序组织。上游组件不决定整个任务是否成功。

## 3. 当前源码中已发现的基础

以下为初步读取结果，完整功能清单还需开发前盘点：

- `app/adapters/extract_worker.py` 已有 7-Zip 路径发现、列表解析和逐文件标准输出解压路径；不是从零接入。
- 现有 worker 仍会按类型使用 Python ZIP/TAR 实现，不能把现有 `7zip` 配置理解成所有格式都由 7-Zip 处理。
- 现有逐文件输出路径包含路径检查、重复输出检查、写入预算、磁盘余量、大小核对和 SHA-256 清单。
- `cue_inputs()` 仍调用旧 helper；`app/services/local.py` 也依赖这一接口，需要迁移。
- 旧 helper 接收递归、ISO 和提层等选项，这些选项的实际调用及效果需要逐项核对。
- `Dockerfile` 当前包含 Go helper 构建阶段，运行镜像复制旧 helper，尚未配套安装官方 7-Zip。
- `tests/` 已复制，但旧 `.gitignore` 忽略了测试、部分文档和 Go 测试。开发基线必须修正相关规则，将必要测试纳入版本管理。

不直接把现有 7-Zip 分支切为默认；先修复和验证其限制，再迁移。

## 5. 7-Zip 适配设计

### 5.1 稳定接口

主程序传入源文件、分卷集合、独立 staging、密码、预算、超时与取消信号；适配层返回文件清单、大小、摘要、组件版本和结构化错误。业务层不解析原始命令行输出。

组件路径解析顺序固定为：显式配置、应用配套组件、经过验证的系统程序。记录最终选择的绝对路径和版本，避免误用旧 p7zip 或缺少 RAR 能力的构建。

### 5.2 解压执行

先获取受限长度、受限时间的条目列表，完成路径、重复、条目数量及声明大小检查，再解压。

优先验证现有逐文件 `-so` 输出方式：由 Python 控制实际写入路径、累计字节、摘要和磁盘余量，避免外部程序直接向最终目录写入。列表格式、特殊文件名、选择条目的精确性及重复条目必须测试；不能假设文本列表总能无歧义解析。

固实 RAR/7z 逐文件提取可能反复解码，性能是主要验证项。如果不可接受，再评估隔离目录批量解压。批量方式只有在路径、特殊文件和输出硬限制得到等价保障后才能采用；轮询目录大小不能声称提供严格预算。无法满足时作为阻塞项说明，不直接降低原有保护。

退出码 0 只是成功条件之一；还需输出清单、大小和完整性检查。警告、错误、空输出及部分输出均不直接进入成功流程。错误分类结合退出码与受限诊断信息；无法可靠区分密码、缺卷或损坏时保留明确的综合错误，不伪造精确结论。

密码不写入持久化命令记录或日志。CLI 密码传递可能对同权限进程可见，需要核实可用输入方式及部署权限边界，不能承诺绝对隐藏。

### 5.3 发布与后处理

每次尝试使用独立 staging，完成全部检查后才发布；跨文件系统时使用明确的复制、校验和完成标记流程，不假设 rename 总能原子完成。任务状态确认成功后才执行现有通知和原包策略。取消及失败输出不允许被后续扫描误认为完成结果。

## 6. 更新机制

是跟随官方 7-Zip 更新，但采用“检查上游候选 → 验证 → 发布兼容版本”，不默认直接安装最新版本。

组件清单记录来源、版本、平台、SHA-256、摘要依据、签名状态、验证记录、实际路径和上一版本。首次选定版本及下载来源在实施时核实，不在本文虚构版本号或平台发布物。

- 默认每天检查，支持关闭与手动检查；只读取元数据，断网或限流显示失败/未知。
- Windows 本机：配套版本按独立目录保存，验证后切换，新任务使用新版，活动任务保留旧路径。系统安装模式只识别和提示版本，不擅自覆盖用户系统安装。
- Linux 容器：构建时安装固定的官方组件，按实际发布物验证 amd64/arm64 支持，通过测试后发布镜像；不在运行容器内自动安装，不挂 Docker socket。
- 官方来源和可用校验机制须核实。自算摘要只能用于追踪；若官方缺少签名或摘要，应由项目验证、发布受控组件清单，清楚区分上游验证与项目验证。
- 本机回滚切换至上一验证组件；容器回滚应用镜像。数据库兼容另行验证，不能将镜像回滚等同于数据库回滚。
- p115 更新仍随应用发布；主程序业务功能不会随 7-Zip 更新自动改变。

为保持轻量，第一版优先交付版本识别、更新检查和固定版本发布。复杂的本机自动下载切换放在核心功能验收之后，不作为启动应用的前提。

## 7. 实施顺序与交付物

1. **盘点与基线**：记录来源提交和本地文档，修正必要的忽略规则，列出功能映射，安装依赖并运行适当的原有检查。交付基线报告；旧 helper 如需构建，仅在新仓库进行。
2. **7-Zip 兼容验证**：核实官方来源、平台与 RAR 能力，复用现有样本，补齐固实包性能、列表歧义、长文件名和安全预算验证。交付兼容报告与未解决项。
3. **适配层改造**：统一列表、受控写入、进程取消及结构化错误，迁移 CUE 和 helper 相关业务能力。交付可对照运行的 7-Zip 实现。
4. **业务及配置迁移**：将 7-Zip 设为默认，旧引擎设置明确迁移或提示不可用；保留其余页面、规则和任务链。交付迁移说明。
5. **部署与更新信息**：调整 Docker 构建，配套官方 7-Zip，增加实际版本和检查状态展示，补充安装与回滚说明。
6. **最终验收及清理**：完成目标平台回归，确认不再调用旧 helper 后，移除 extractor 和 third_party/xtractr 及对应构建步骤；按依赖使用情况更新许可证，不能一并误删其他依赖声明。

每阶段独立提交，附验证结果；不把业务重写、项目全面改名和数据库重构混入解压替换。迁移期间旧实现只用于对照和回退，最终只保留一个生产解压引擎。

## 8. 测试与通过标准

复用并调整 `tests/test_extract_formats.py`、`tests/test_local.py`、`tests/test_output_cleanup.py`、`tests/test_unpackflow_compat.py` 等测试；后者逐项保留业务要求，移除对旧 helper 实现细节的绑定。补充取消、任务隔离和通知链回归，完整名单以盘点为准。

真实 7-Zip 测试不能因未安装工具而全部跳过后仍宣称验收通过。RAR 样本需有可分发来源和确定预期，不能用改扩展名的 ZIP 代替；记录测试工具版本、操作系统和结果。

最终通过条件：功能映射无遗漏；关键错误场景不误报成功；失败不误删原包；取消不发布残留；预算和路径策略有效；固实包性能可接受；目标部署平台可运行；版本可追溯且回退经过验证。差异或未测项单独列出，不视为通过。
