# 官方 xt v0.3.0 实测结论

测试日期：2026-11-04。结论：可以直接安装运行，但当前版本不符合本项目直接替换要求。

## 环境与可信范围

- 使用 Unpackerr/xt 官方 v0.3.0 Windows amd64 发布包。
- 二进制自报：xt v0.3.0-71，revision 9a0fd7a。
- ZIP SHA-256：2586450039988bc4bc03923949b6f1bc16ba9ce0ad0b28ba9033ecea624fcca6，与同一官方发行版 checksums 文件一致。
- 未验证独立发布者签名，因此不能将此次摘要比对称为完整真实性认证。
- 全部输入为隔离测试目录生成的样本；未替换现有 helper，未操作真实业务文件。
- 本次执行了 Windows 版本，Linux/NAS 平台尚未执行；以下关键失败现象与前次固定版本源码核查一致。

## 替换判定

当前不应把 xt v0.3.0 直接设置成生产默认解压后端。阻塞项：

1. 错误返回 0，且没有稳定的机器结果协议；易造成错误密码或损坏包被当作成功。
2. 未暴露写出大小和条目数量预算，不能保留现有运行中限制。
3. 重复输出处理和嵌套行为不一致，直接替换会改变功能和安全策略。

解析日志中的 ERROR 可以作为诊断辅助，不能作为完整的生产成功判定协议；扫输出目录也无法区分空包、失败和部分成功。不能仅包装一层进程调用就宣布等价兼容。

## 推荐下一步

继续采用“主程序调用独立解压程序”的边界，但暂时使用现有 helper。

优先验证第二条路线：极薄 helper 使用 Go module 依赖官方 xtractr 固定版本，不复制整个解码源码，不使用本地 replace。保留 JSON 结果、预算和安全校验，将解码维护交给上游，helper 单独构建发布和更新。

该路线仍需验证最新上游对当前安全补丁、CUE、长路径和嵌套逻辑的覆盖，不能直接删除 vendored 代码。若上游库不足，再明确列出必要补丁；也可等待或推动官方 xt 增加机器接口及预算参数。

本次未实测：RAR、缺卷、多卷恢复、ISO/UDF、CUE 音轨、长路径边界、符号链接、Linux 资源隔离及内存峰值。由于已有明确阻塞项，不继续扩大这些测试来推迟选型结论。
